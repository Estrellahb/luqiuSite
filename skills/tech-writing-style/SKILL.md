# 面向初学者的技术写作风格指南

## 核心定位
以**资深工程技术人员向初学者沟通**的视角，讲清楚“系统背后是如何工作的”，保持专业、平实与客观，避免居高临下的说教感。

---

## 核心原则

### 1. 摒弃二元对立句式（严禁“不是……而是……”）
- **问题**：“不是 A 而是 B”带有强烈的纠错与说教色彩，打断读者的理解节奏，属于信息冗余的否定式转折。
- **做法**：删除先否后肯的套路，**直接阐述真实原因或正向结论**。
- **对比**：
  - ❌ *报错不是惩罚，而是计算机在向你明确汇报问题。*
  - ✅ *计算机抛出报错，本质是一份实时生成的排查日志，记录了故障的具体位置与触发原因。*

### 2. 直述工作机制，给出因果链路
- 初学者的困惑往往来自于“黑盒”操作。解释一个概念时，重点说明**数据流向、物理状态或系统行为**。
- 说明“因为系统底层发生了什么，所以表现出了这个现象”。
- **对比**：
  - ❌ *这不是电脑配置差，而是你装了流氓软件。*
  - ✅ *电脑变慢的根本原因，是后台被静默启动了多个常驻进程，大量占用了 CPU 算力与内存带宽。*

### 3. 用贴切工程隐喻降低认知成本
- 当术语过于抽象时，使用日常工程生活中的实体（如通行证、中间门卫、体检单、快递分发站）作为类比。
- **注意**：隐喻要紧贴真实机制，类比后立即收拢到实际技术细节上，避免比喻失真。
- **示例**：
  - *Cloudflare 源站证书就像两台内部服务器之间的专用通行证，只供边缘节点和源站通信校验，因此无需通过公网权威 CA 机构的根证书验证。*

### 4. 给出行动支点与工程价值
- 不只告诉读者“怎么做”，还要顺带点出“为什么行业通用这种做法”或“带来哪些收益”。
- 让读者建立起架构和链路思维（例如：链路打通、暴露风险、安全边界、资源隔离）。

---

## 典型改写对照表（Checklist）

| 禁忌/低效表述 | 推荐改写方式 | 核心要点 |
| :--- | :--- | :--- |
| **“不是……而是……”** | 直接叙述事实与正向逻辑，省去无效否定 | 去掉多余纠错感，单刀直入 |
| **“其实很简单……” / “显而易见……”** | 给出具体判定依据和步骤 | 尊重初学者的认知难度，不预设立场 |
| **只贴报错让用户自己看** | 拆解日志结构：在哪一行、什么类型、为什么触发 | 传授排查与看日志的思维方法 |
| **只说“这样更安全”** | 解释风险面：直接暴露公网 IP 会导致什么攻击 | 讲清因果，建立工程安全感 |

---

## 审查触发词与自查
在输出或润色文档时，自查是否包含以下词汇：
- 检索：`不是.*而是`、`并非.*而是`
- 检查语气：是否存在教导语气？是否有未解释清楚机制的黑盒结论？
