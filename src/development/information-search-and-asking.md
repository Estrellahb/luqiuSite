# 信息搜索与提问方法

本文参考：[《提问的智慧》](https://github.com/ryanhanwu/How-To-Ask-Questions-The-Smart-Way/blob/main/README-zh_CN.md)。

开发过程中，遇到问题是很正常的。真正影响解决效率的，往往不是问题本身，而是搜索和提问方式。

一个清晰的问题，通常至少需要说明三件事：

1. 做了什么。
2. 得到了什么结果。
3. 希望达到什么结果，或者需要获得哪方面的帮助。

例如：

> 在 Windows 11 中安装 Node.js v22.23.2 后，通过 Git Bash 执行 `node --version`，提示 `command not found`。已经重新打开终端，但问题仍然存在。希望确认 Node.js 是否安装成功，以及应该如何检查环境变量。

这个问题包含了操作环境、执行步骤、实际结果、已经尝试过的处理方式和期望结果，其他人或 AI 可以据此开始排查。

遇到问题时，可以直接提供报错截图或文字。但在提问前，应先阅读和理解报错内容。英文报错可以先翻译成中文，确认其中提到的文件、依赖、权限、路径或版本问题。

如果报错信息已经明确说明缺少某个文件或依赖，可以先按照提示进行安装或修复，再继续排查。提问的目的在于解决无法独立判断的问题，不能完全跳过阅读报错、搜索资料和基础尝试的过程。

本文分为两个部分：

1. 浏览器与搜索引擎
2. 与 AI 对话

## 浏览器与搜索引擎

### 浏览器与搜索引擎的区别

浏览器是访问网站和运行网页应用的软件，例如 Google Chrome、Microsoft Edge 和 Firefox。

搜索引擎是用于检索网页信息的服务，例如 Google、Bing 和百度。浏览器和搜索引擎并不是同一个概念。Chrome 只是浏览器，打开后可以使用 Google、Bing、百度或其他搜索引擎。

### Google 搜索

开发资料优先推荐使用 Google 搜索。Google 对英文官方文档、GitHub 项目、技术博客、视频网站和开发者社区的收录较为完整，搜索结果通常也更适合定位开发问题。

由于网络环境限制，部分地区可能无法直接访问 Google，需要根据实际情况配置网络代理。使用 Chrome 配合去广告扩展，可以减少页面干扰，提高阅读效率。

英文搜索词的覆盖范围通常更广。掌握常见技术词汇后，可以直接搜索英文报错、软件名称、版本号和官方文档。例如：

```text
Node.js v22.23.2 Git Bash command not found
```

```text
Docker Desktop Windows WSL 2 installation
```

```text
VuePress failed to resolve component
```

搜索结果中可以重点关注：

- 官方网站和官方文档
- GitHub 官方仓库
- 项目的 Issues、Discussions 和 Releases
- Stack Overflow 等技术问答社区
- 维护者的博客或公告

### Bing 搜索

Bing 可以作为 Google 的补充。

在没有代理，或者 Google 没有找到合适结果时，可以使用 Bing 搜索。部分国内网站、中文教程和微软生态相关资料，在 Bing 中也比较容易找到。

### 百度搜索

百度对于中文内容的覆盖范围较大，适合搜索国内软件、国内服务、中文教程和本地化解决方案。

不过，百度搜索结果中的广告和推广内容较多，信息质量差异也比较大。搜索软件、下载工具或访问服务时，需要仔细区分广告、推广页面和真实官网。

### 如何确认官方网站

不能仅凭域名后缀判断网站是否为官方网站。`.com`、`.org`、`.cn` 等只是顶级域名，任何符合注册条件的个人或组织都可能使用，域名后缀本身不能证明网站可信。

确认官方网站时，可以检查以下内容：

1. 通过项目官方 GitHub 仓库中的链接进入下载页面。
2. 通过官方网站的文档页、下载页或联系方式交叉确认。
3. 核对域名拼写，注意多余字符、连字符和相似字母。
4. 检查页面是否使用 HTTPS。
5. 对比官方仓库、官网和社区公告中的下载地址。
6. 不要仅根据搜索结果标题或广告内容判断页面身份。
7. 不要随意下载弹窗推荐的安装包、破解软件或不明压缩包。

即使使用 HTTPS，也只能说明连接经过加密，不能单独证明网站就是官方站点。下载软件时，官方仓库和官方网站之间应能够相互对应。

### 搜索时如何组织关键词

搜索关键词应包含具体对象、版本和问题现象。

不推荐：

```text
代码运行不了
```

推荐：

```text
Python requests SSL certificate verify failed
```

不推荐：

```text
怎么安装 node
```

推荐：

```text
Node.js v22.23.2 Windows installation
```

搜索时可以逐步补充以下信息：

- 操作系统和版本
- 软件名称和版本
- 使用的编程语言或框架
- 完整报错信息
- 执行过的命令
- 预期结果
- 实际结果

如果搜索结果过多，可以使用更具体的限定方式：

```text
site:github.com Node.js Git Bash command not found
```

```text
site:docs.docker.com Docker Desktop Windows WSL 2
```

```text
"具体报错内容"
```

直接搜索完整报错信息，通常比描述“程序无法运行”更容易找到对应的解决方案。

## 与 AI 对话

### AI 不能替代判断

进入 AI 时代后，搜索和提问仍然重要。AI 可以帮助解释资料、分析报错、整理思路和生成代码，但返回内容不能直接视为正确答案。

AI 可能出现以下问题：

- 把旧版本信息当成当前版本信息。
- 编造不存在的配置项、命令或链接。
- 混淆不同系统、框架和软件的使用方法。
- 忽略代码上下文，给出表面上合理但无法运行的方案。
- 对不确定的问题给出过于肯定的回答。

涉及删除文件、修改系统配置、部署服务、处理密钥、安装未知软件或执行高风险命令时，需要先确认方案的影响范围，再决定是否执行。

涉及健康、安全、财务、法律和生产环境的问题，不能只依赖 AI 的回答。AI 给出的建议需要通过专业资料、官方文档或专业人员进一步确认。

### 向 AI 提问前需要准备什么

向 AI 提问前，建议整理以下信息：

- 想要完成的目标
- 当前使用的系统和版本
- 项目使用的语言、框架和工具
- 已经完成的操作
- 完整报错信息
- 相关代码或配置
- 期望结果
- 已经尝试过的解决方法
- 不允许修改的文件或配置
- 希望 AI 返回的内容形式

这些信息越完整，AI 越容易理解上下文，也越容易给出可以执行和验证的方案。

### 推荐的提问结构

可以使用以下模板：

```text
目标：
希望完成什么事情。

背景：
使用的操作系统、项目、语言、框架、软件和版本。

现状：
已经完成了什么，当前遇到了什么问题。

材料：
相关代码、配置文件、日志、报错信息或参考链接。

已尝试：
已经执行过哪些操作，得到什么结果。

限制：
哪些文件不能修改，哪些方案不能使用，是否不能部署或提交代码。

输出要求：
希望 AI 返回解释、排查步骤、代码、补丁、配置示例，还是修改后的完整文件。
```

例如：

```text
目标：
排查 Node.js 安装后 Git Bash 无法识别 node 命令的问题。

背景：
系统是 Windows 11，安装的 Node.js 版本为 v22.23.2，终端使用 Git Bash。

现状：
执行 node --version 后提示 command not found。

已尝试：
已经重新打开 Git Bash，但问题仍然存在。

限制：
暂时不要修改系统文件，也不要重新安装其他软件。

输出要求：
请先解释可能原因，再给出检查 PATH 环境变量的步骤，不要直接假设已经找到根本原因。
```

### 如何让 AI 更好地参与开发

AI 适合参与以下工作：

- 解释开发概念和报错信息。
- 根据需求拆分任务。
- 帮助整理项目目录和文件职责。
- 讨论技术方案和实现边界。
- 编写或修改代码。
- 编写测试用例。
- 分析日志和构建结果。
- 检查代码中的潜在问题。
- 整理文档、注释和提交说明。

开发任务不宜只用一句“帮忙写一个项目”开始。更稳妥的方式，是先与 AI 讨论目标、用户、功能、数据、页面、接口、权限、错误处理和验收标准，再进入具体实现。

可以先要求 AI：

1. 阅读现有项目结构。
2. 复述对需求的理解。
3. 列出不确定的内容。
4. 给出实现方案。
5. 等待确认后再修改文件。
6. 完成修改后说明改动范围。
7. 执行测试或构建。
8. 根据真实执行结果报告问题。

### AI 返回结果后需要做什么

AI 给出回答后，不应直接复制和执行。需要进行以下检查：

- 命令是否适用于当前操作系统。
- 软件版本是否与当前环境一致。
- 文件路径是否真实存在。
- 配置项是否来自官方文档。
- 代码是否符合当前项目结构。
- 是否会覆盖已有修改。
- 是否包含删除文件、清空数据或修改权限的操作。
- 是否泄露 API 密钥、密码、Cookie 或内部地址。
- 是否通过实际运行、测试或构建验证。

如果 AI 的回答不完整或无法理解，可以继续追问：

```text
请解释这条命令中每个参数的作用。
```

```text
这个方案适用于 Windows 11 和 Node.js v22.23.2 吗？请说明判断依据。
```

```text
请不要直接修改文件，先列出准备修改的文件和每个文件的影响。
```

```text
请根据上一条报错重新分析，不要重复已经失败的方案。
```

```text
请给出官方文档链接，并说明这条结论对应文档中的哪一部分。
```

### AI 不确定时怎么办

如果 AI 的知识不足，可以补充更多上下文，也可以要求 AI 继续拆解问题、列出假设和验证方法。

需要注意，追问的目的不是让 AI 一直生成更长的答案，而是逐步缩小问题范围。每次追问后，都应检查是否获得了新的事实、操作步骤或验证依据。

当 AI 给出多个可能原因时，可以要求它按照可能性和验证成本排序：

```text
请列出最可能的三个原因，并按照优先级排序。每个原因提供一个不会破坏现有环境的验证方法。
```

当问题涉及最新版本、具体项目或官方配置时，应要求 AI 先查阅官方文档，或者自行打开官方来源进行确认。AI 生成的链接、命令和版本信息，都需要通过真实来源和实际运行结果验证。

搜索引擎适合定位资料，AI 适合整理、解释和协助执行。两者可以结合使用，但最终判断仍然需要建立在可靠来源、明确上下文和实际验证的基础上。
