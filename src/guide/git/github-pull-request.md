# GitHub Pull Request 协作流：从提 PR 到参与开源

在前面的章节中，我们已经能够在自己的电脑上开辟分支、解决代码冲突并将代码同步到云端。

但在实际工作团队或全球开源社区中，**任何人都不会（也不应该）拥有直接往 `main` 主分支上推代码的权限**。所有的代码合并，都必须经过一道规范的质量关卡——这就是 **Pull Request（简称 PR，中文通常称为"合并请求"）**。

本篇我们将拆解 Pull Request 的运作逻辑，带你跑通团队内部分支协作与参与公共开源项目（Fork 流）的完整全景。

---

## 一、究竟什么是 Pull Request？

"Pull Request"直译过来是"拉取请求"。它的字面意思其实很通俗：
> *"嗨，仓库管理员！我在我自己的独立分支（或我的副本）上写好了一个新功能，**请求你把我的改动拉取（Pull）合并到你们的主分支中**。"*

```text
[ 开发者提交的 feature 分支 ]
            │
            ▼ 发起 Pull Request
┌──────────────────────────────────────┐
│       GitHub 网页端审查大厅           │
│  - 自动化检查（测试是否通过？）      │
│  - 人工审查（团队成员逐行 Code Review）│
│  - 沟通讨论与进一步修改              │
└──────────────────────────────────────┘
            │
            ▼ 审查通过，点击「Merge」
[ 目标仓库的 main 主分支 ]
```

### PR 带来的三大工程价值
1. **防止事故直接污染主干**：主干分支保持稳定，只有经过审查与自动化测试验证的代码才能合入；
2. **可视化的代码审查（Code Review）**：团队成员可以在 GitHub 网页上直接对某一行代码发表评论、提出修改建议，相互学习与把关；
3. **沉淀历史决策背景**：每一个 PR 都记录了当时"为什么要加这个功能"、"遇到了什么分歧"、"最后如何解决"，成为项目最宝贵的档案。

## 二、场景一：团队内部的 PR 协作流

在公司或固定小团队中，大家通常都在**同一个代码仓库**内协作：

### 规范操作链路
1. **开辟分支**：本地基于最新的 `main` 创建一个新分支（例如 `feature/add-avatar`）；
2. **编写并提交**：在分支上完成代码编写并 Commit；
3. **推送到云端**：将这个分支推送到 GitHub（在 VS Code 点击发布分支）；
4. **发起 PR**：
   - 打开 GitHub 网页端进入该仓库，页面顶部会自动弹出一个黄色提示框：`feature/add-avatar had recent pushes`，右侧有一个绿色的 **「Compare & pull request」** 按钮；
   - 点击该按钮，进入 PR 填写页面；
5. **填写 PR 标题与描述**：
   - **Title（标题）**：简明扼要概括（例如 `feat: 用户个人中心支持上传自定义头像`）；
   - **Description（详细描述）**：说明改动动机、做了哪些改动、附上效果截图；如果关联了某个缺陷单，写上 `Fixes #12`，合并后系统会自动帮你关闭 12 号 Issue；
6. 点击绿色的 **「Create pull request」**，合并请求正式发布！

## 三、场景二：参与开源项目的黄金流（Fork 工作流）

如果你想给 Vue、React、或者任何第三方的开源项目修一个 Bug、补充一段文档，你显然是没有该仓库的直接推送权限的。

此时必须采用开源界通用的 **Fork 工作流**：

```text
[ 他人的上游源仓库 (Upstream) ]
       │
       ▼ 点击网页右上角的「Fork」按钮
[ 你自己 GitHub 账号下的副本仓库 (Origin) ]
       │
       ▼ clone 到本地写代码并 push 回你的副本
[ 发起跨仓库的 Pull Request ] ───────→ [ 提交给上游原作者审核合并 ]
```

### 1. 第一步：Fork 项目到自己的账号
打开目标开源项目的 GitHub 页面，点击页面右上角的 **「Fork」** 按钮。
- **底层行为**：GitHub 会在你的个人账号下，完整克隆一份一模一样的仓库副本。你对这个副本拥有 100% 的读写权限。

### 2. 第二步：将你的副本克隆到本地开发
使用 VS Code 或终端，将**你个人账号下的那个副本**克隆到本地电脑：
```bash
# 注意地址是你自己主页下的仓库
git clone git@github.com:your-username/repo-name.git
```
在本地创建新分支、修改代码、测试无误后，提交并推送（Push）回你自己的 GitHub 仓库。

### 3. 第三步：向上游原仓库发起跨仓库 PR
1. 回到你自己的 GitHub 仓库页面，点击「Contribute」`→`「Open pull request」；
2. GitHub 会自动识别：
   - **base repository（目标上游）**：原作者的仓库 `main` 分支；
   - **head repository（来源仓库）**：你自己副本仓库的那个新分支；
3. 仔细填写描述，遵循该开源项目的贡献准则（Contributing Guidelines），点击提交；
4. 原项目的作者与维护者会收到通知，对你的代码进行审查，最终点击合并！你的名字就会永久列在该项目的 Contributor 贡献者列表中。

## 四、PR 被要求修改时怎么办？（无需关闭 PR）

很多初学者提了 PR 后，如果维护者提了修改意见（Code Review Comments），经常会慌张地把 PR 关掉，重新建一个——**这是完全多余的**。

**PR 是一个活生生的、持续监听的通道**：
- 只要 PR 还没有被关闭或合并，你只需要在**本地原来的那个分支上继续修改代码并 Commit**；
- 再次执行 `push` 推送到云端；
- **GitHub 上的那个 PR 页面会自动同步追加你最新的提交！** 维护者刷新页面就能看到你的最新修正。

## 五、GitHub 合并 PR 的三种方式解析

当代码审查通过后，仓库管理员点击绿色的合并按钮时，下拉菜单里通常有三个选项：

| 合并方式 | 底层行为 | 优缺点与适用场景 |
| :--- | :--- | :--- |
| **Create a merge commit** | 在主干上新生成一个特殊的"双亲"合并节点，完整保留分支上的每一个琐碎 Commit | **优点**：历史原汁原味全部保留；<br>**缺点**：如果分支上有很多无意义提交，会让主线历史显得杂乱 |
| **Squash and merge（最推荐）** | 将你在该分支上的所有提交**"压扁压平"打包成唯一一个干净的大提交**合入主干 | **优点**：主干时间线极为清爽整洁，每个 PR 对应主干上的一个单一节点，排查回滚极方便；<br>**适用**：绝大多数团队日常业务开发的黄金法则 |
| **Rebase and merge** | 将分支的所有提交逐个拔下来，嫁接到主干的最新头部 | **优点**：形成一条笔直无分叉的时间线；<br>**注意**：会重写提交哈希，对团队规范要求较高 |

---

::: tip 保持你的 Fork 仓库与原作者同步
当你 Fork 了一个开源项目很长时间后，原作者可能已经更新了几百次代码。如何在不重新 Fork 的前提下跟上原作者的进度？

非常简单！在你自己 GitHub 副本仓库的主页上，分支名称旁边有一个醒目的 **「Sync fork」** 按钮：
- 如果落后了上游代码，按钮会提示 `This branch is out of date`；
- 直接点击 **「Sync fork」`→`「Update branch」**，GitHub 就会自动拉取原作者的最新主干，与你的副本无损合二为一！
:::
