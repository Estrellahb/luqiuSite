# 单人核心操作流与安全红线

在上一篇中，我们完成了 Git 的安装与通信链路打通。现在，我们可以正式开始用 Git 来管理实际项目了。

许多初学者在刚开始用 Git 时，经常会有这样的疑惑：
- *"为什么每次保存代码，非要先 `git add` 然后再 `git commit`，这不是多此一举吗？"*
- *"为什么别人的提交历史看起来清晰明了，而我的历史里全是'update'和'修bug'？"*
- *"为什么有人把代码推到 GitHub 后，云服务账户瞬间被盗刷扣费？"*

这一篇我们将拆解 Git 底层的数据流转模型，建立规范的日常提交闭环，并划清不容触碰的代码安全红线。

---

## 一、Git 的三层数据结构与状态流转

在本地，Git 管理文件变动并不直接跨越到历史档案中，而是在内部设计了三个工作区域：

```text
[ 本地硬盘目录 ]              [ 索引缓冲区 ]              [ 历史档案库 ]
┌────────────────┐          ┌────────────────┐          ┌────────────────┐
│     工作区     │          │     暂存区     │          │   本地版本库   │
│ (Working Tree) │ ──add──→ │ (Staging Area) │ ─commit─→│  (Repository)  │
│                │          │                │          │                │
│ 实际编辑的文件 │          │ 挑选准备提交的 │          │ 永久保存的快照 │
└────────────────┘          └────────────────┘          └────────────────┘
```

### 1. 三层区域的职责分工
- **工作区（Working Tree）**：你在操作系统文件夹中直接看到、并在编辑器（如 VS Code）里实时编写的文件和目录；
- **暂存区（Staging Area / Index）**：位于 `.git/index` 的一块缓冲区。它记录了你**准备在下一次快照中打包**的文件清单与内容变动；
- **本地版本库（Repository / HEAD）**：位于 `.git` 目录下的核心对象库，保存着所有已经完成的 Commit 快照，构成了不可篡改的历史记录链条。

::: info 为什么需要设计"暂存区"？
很多初学者会觉得"直接把修改存入版本库更省事，暂存区纯属多余"。

从软件工程角度看，暂存区的核心价值在于**提供精细化挑选改动的能力（保持原子化提交）**：
- 假设你在一天的工作中修改了 5 个文件，其中 3 个文件是为了实现"用户登录功能"，另外 2 个文件是顺手修复了"首页排版样式"；
- 如果直接全量保存，这两批逻辑完全无关的改动就会混在同一个快照中，后续一旦登录逻辑出现故障需要单独回滚，首页样式也会被强行连带撤销；
- 暂存区的存在，允许你先通过 `git add` 挑出那 3 个登录文件打包提交一次；再挑出剩余 2 个样式文件打包提交第二次。这种让每一次提交只聚焦于一个独立变动的原则，称为**原子化提交（Atomic Commit）**。
:::

---

### 2. 文件在 Git 眼中的四种生命周期状态

| 文件状态 | 物理含义 | 触发时机 |
| :--- | :--- | :--- |
| **未跟踪（Untracked）** | 新建的文件，Git 尚未将其纳入版本管理 | 在项目文件夹中新创建了一个文件 |
| **已修改（Modified）** | 已被追踪的文件，内容发生了变动但未准备提交 | 在编辑器中对老文件敲了新代码、保存了修改 |
| **已暂存（Staged）** | 修改已被放入缓冲区，等待写入下次快照 | 执行了 `git add` 之后 |
| **未修改（Unmodified）** | 文件最新内容与版本库快照完全一致 | 刚刚执行完 `git commit` 之后 |

## 二、单人开发标准闭环：核心三板斧

### 1. 初始化本地仓库（`git init`）
在一个尚未被 Git 管理的项目文件夹根目录下，打开终端运行：

```bash
git init
```

**底层行为**：Git 会在该目录下自动创建一个名为 `.git` 的隐藏文件夹。这个文件夹就是你这台电脑专属的"版本档案馆"，后续所有的提交历史、分支指针和元数据都保存在其中。

---

### 2. 状态巡检仪（`git status`）

```bash
git status
```

终端常见输出解读：
- **红色文件名（Untracked / Modified）**：提示这些变动还在工作区，尚未加入暂存区；
- **绿色文件名（Changes to be committed）**：提示这些变动已经进入暂存区，随时可以执行 `commit` 打包；
- **nothing to commit, working tree clean**：代表所有修改都已经提交到了版本库，当前工作区是完全干净的。

::: tip 极简模式：更高效的日常状态查看
加上 `-s` 参数可以输出紧凑格式，方便快速浏览大量修改：
```bash
git status -s
```
- `?? file.txt`：未跟踪的新文件；
- ` M file.txt`：工作区已修改，未暂存；
- `M  file.txt`：已暂存，等待提交。
:::

---

### 3. 挑选放入暂存区（`git add`）

```bash
# 暂存单个指定文件
git add src/index.js

# 暂存特定目录下的所有变动
git add src/components/

# 暂存当前目录下的全部变动（日常最常用）
git add .
```

---

### 4. 永久写入历史快照（`git commit`）

```bash
git commit -m "提交说明信息"
```

::: info 行业通用规范：Conventional Commits（约定式提交）
清晰的提交说明是未来追溯代码改动原因、定位故障责任人的核心索引。行业内广泛采用 **Conventional Commits（约定式提交）** 规范。

标准的提交信息结构格式为：
```text
<type>(<可选 scope>): <改动描述>
```
- **`type`（类型）**：必填，表明本次提交在工程中的性质类别；
- **`scope`（作用域）**：选填，表明改动具体影响的模块或目录（如 `auth`、`navbar`）；
- **`<改动描述>`**：必填，简明扼要的动宾短语，直接阐明这次修改解决了什么问题。

#### 常见提交类型（Type）全景对照表

| 提交前缀（Type） | 物理含义 | 适用场景 | 优秀范例 |
| :--- | :--- | :--- | :--- |
| **`feat:`** | 新功能（feature） | 为产品引入了全新的业务功能或界面组件 | `feat: 增加用户登录界面的手机号验证` |
| **`fix:`** | 缺陷修复（bug fix） | 修复了系统运行中被发现的报错、异常或显示错误 | `fix: 修复深色模式下顶部导航栏文字对比度过低的问题` |
| **`docs:`** | 文档变更（documentation） | 仅对 README、项目文档、注释进行了修改 | `docs: 补充 API 文档中的请求参数说明` |
| **`style:`** | 代码格式（formatting） | 仅调整排版与代码格式，不影响执行逻辑 | `style: 统一代码缩进为两个空格` |
| **`refactor:`** | 代码重构（refactoring） | 对既有代码结构进行重构，既非新功能也非修 Bug | `refactor: 将冗长的订单校验函数拆分为独立验证器` |
| **`perf:`** | 性能优化（performance） | 专门针对运行速度、首屏渲染或内存消耗的性能提升 | `perf: 将首页大图转换为 WebP 格式以提升加载速度` |
| **`test:`** | 测试相关（tests） | 新增单元测试、集成测试或修改已有测试用例 | `test: 增加密码强度校验工具函数的边界单元测试` |
| **`chore:`** | 杂项维护（routine chores） | 构建流程配置、辅助脚本调整、依赖包升级等琐事 | `chore: 升级 vite 版本至 5.x` |
| **`revert:`** | 版本撤销（reversion） | 用于撤销某次历史提交 | `revert: 撤销上一条误提交的测试代码` |

#### 正反范例对比

- ✅ **高效清晰**：
  - `feat(cart): 增加购物车商品批量删除功能`
  - `fix: 修复 Safari 浏览器中日期选择器无法弹出的问题`
- ❌ **低效模糊（应坚决规避）**：
  - `update`（完全无法得知究竟改动了什么）
  - `111` / `fix bug` / `temp`（无任何检索价值的占位符）
:::

---

### 5. 查看版本历史（`git log`）

```bash
# 完整模式：查看详细作者、时间戳、Commit 哈希及说明
git log

# 单行简洁模式（推荐高频使用）
git log --oneline

# 树状图形模式：直观展示分支与提交分叉结构
git log --oneline --graph --all
```

终端输出示例：
```text
* d4e1a2f (HEAD -> main) docs: 补充 README 部署指引
* 8b3c90e feat: 新增用户注册表单页面
* 1a2b3c4 init: 初始化项目工程骨架
```

## 三、不可忽视的安全红线：`.gitignore`

许多初学者会养成一个习惯：写完代码不管三七二十一，直接敲 `git add .` 然后一股脑推到 GitHub。

**这种习惯存在严重的安全隐患和工程隐患。**

### 1. 绝对不能提交到仓库的文件类型

1. **依赖库与第三方包**：
   例如前端的 `node_modules/`、Python 的虚拟环境 `venv/`。这些文件夹体积动辄几百兆甚至数个 G，应该通过依赖清单（如 `package.json`、`requirements.txt`）由开发者在本地重新安装；
2. **构建产物与临时文件**：
   例如打包生成的 `dist/`、`build/`、系统生成的桌面缓存 `.DS_Store`、`Thumbs.db` 以及运行日志 `*.log`；
3. **敏感凭证与商业机密（最高危）**：
   例如包含数据库密码、云厂商 AccessKey、OpenAI API Key 的本地环境变量文件（`.env`、`config.secret.json` 等）。

::: caution 为什么敏感配置泄露是一场灾难？
GitHub 等公开平台常年被黑客的自动化脚本全天候爬取。

只要你将带有真实 API Key 或云服务器密码的配置文件推送到公网：
1. **数秒内即可被脚本自动截获**，你的云账户可能被用于批量开辟高配算力挖矿，造成上万元的经济损失；
2. **事后在本地删除文件是完全无效的**：因为 Git 的物理机制是保留完整的历史快照。即使你发布了"删除该密码文件"的新提交，黑客只需翻阅你的上一条历史 Commit，依然能原封不动地读出被删除的密码！
:::

---

### 2. `.gitignore` 的工作机制与规则语法

在项目根目录下创建一个名为 **`.gitignore`** 的纯文本文件（以点开头，没有扩展名）。Git 在扫描工作区时，会自动忽略所有匹配该规则的文件，使它们**永远不会出现在 `git status` 的未跟踪列表**中。

```gitignore
# 1. 忽略特定名称的文件夹（在名称后加上斜杠）
node_modules/
dist/
venv/

# 2. 忽略特定后缀的所有文件（使用星号通配符）
*.log
*.tmp

# 3. 忽略特定名称的敏感配置文件
.env
.env.local
config.private.json

# 4. 忽略操作系统自动生成的垃圾文件
.DS_Store
Thumbs.db

# 5. 取反规则：即便上面排除了所有的 .log，但不排除 debug.log（使用叹号）
!debug.log
```

::: tip 行业黄金准则
**在对新项目执行第一次 `git add .` 之前，第一件必须做的事就是建立 `.gitignore` 文件。**

如果你不知道当前技术栈应该忽略哪些文件，可以直接使用社区维护的开源模板库：
访问 [github/gitignore 官方模板仓库](https://github.com/github/gitignore)，直接搜索并下载对应语言（如 Node.gitignore、Python.gitignore）的成熟配置。
:::

---

### 3. 应急补救：不小心把忽略文件提交进去了怎么办？

如果你在配置 `.gitignore` 之前，就已经执行了 `git add` 甚至已经 `commit`，此时再把文件名写入 `.gitignore` 是不会自动生效的。

**正确解法：仅从版本库追踪中移除，但保留本地磁盘文件**
```bash
# 移除单个文件的版本追踪
git rm --cached .env

# 递归移除整个依赖目录的版本追踪
git rm -r --cached node_modules/
```
执行后，再运行 `git commit -m "chore: 移除受跟踪的敏感/依赖文件"`。这样该文件就会从未来的版本历史中被剥离，同时保留在你本地硬盘上不被物理删除。

## 四、单人日常操作完整演练

```bash
# 1. 进入项目根目录并初始化仓库
cd my-new-project
git init

# 2. 【核心第一步】编写 .gitignore 文件，防止误传杂质
echo "node_modules/" >> .gitignore
echo ".env" >> .gitignore

# 3. 查看当前目录状态
git status

# 4. 将所有合法变动放入暂存区
git add .

# 5. 打包为第一次版本快照
git commit -m "init: 完成项目初始化与基础配置"

# 6. 编辑修改了 index.html 页面，再次查看变动
git status -s

# 7. 将修改后的 index.html 暂存并提交
git add index.html
git commit -m "feat: 完成首页轮播图组件开发"

# 8. 查看已记录的版本历史线
git log --oneline
```
