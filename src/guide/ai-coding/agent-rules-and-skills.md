# Agent 驯服实战：从 Prompt 心法、Skills 注入到 AGENTS.md 宪法

在前面几篇中，我们完成了终端 Coding Agent 的选型，并且理解了底层大模型与四大工具的协作回路。

然而，许多初学者第一次唤起 Agent 尝试让它干活时，往往会立刻遭遇一系列令人抓狂的“翻车现场”：
- *“让它帮忙改个接口逻辑，它却顺手把你辛苦写好的几十行注释全部删光，甚至擅自重构了无关的文件；”*
- *“明明项目使用的是 pnpm，它却自作主张执行了 `npm install`，生成了一堆破坏依赖树的 `package-lock.json`；”*
- *“每次新开一个终端窗口，你都得心力交瘁地把‘必须用 TypeScript’、‘代码命名要用小驼峰’这些规矩重新手动给它敲一遍……”*

这些问题的根源，并不是底层模型“太笨”，而是因为：**你让一个刚入职的顶级工程师在‘空脑上岗’——你既没有给他合理的任务指令，也没有给他查阅业务规章的途径，更没有给他立下严苛的项目宪法。**

本篇我们将从微观的单次指令，层层推进到项目全局约束，拆解 **Prompt 的工程高度**、**Skills 的渐进式技能加载**，以及如何打造一份坚固的 **`AGENTS.md` 项目宪法**。

---

## 一、Prompt 的工程高度：如何下达高质量指令？

很多初学者习惯用和真人闲聊的方式指挥 Agent：“帮我看看这段代码，改得好看点”。这种指令极其模糊，大模型只能凭空猜想，结果往往大失所望。

而在另一个极端，有些同学把指令写成了一连串密不透风的死板流程图（“如果 A 发生了就点 B，如果 B 没反应就试 C”），一旦代码出现微小的非预期异常，这种死板规则就会瞬间崩溃。

在国际前沿的 Agent 工程体系中，这被称为 **“指令高度（Prompt Altitude）”的权衡**：

```text
┌─────────────────────────────────────────────────────────────┐
│ ❌ 飞得太高 (Too High / 过于模糊抽象)                       │
│ "把项目弄好一点，加个用户功能，优化一下体验"               │
│ 后果: 大模型只能靠概率瞎猜，改出大量无法落地的伪代码        │
├─────────────────────────────────────────────────────────────┤
│ ❌ 飞得太低 (Too Low / 过于死板僵化)                        │
│ "第一步打开第 3 行，把 a 改成 b，然后看终端第 2 个单词..."  │
│ 后果: 剥夺了模型的推理能力，稍微遇到环境不一致就直接死循环  │
├─────────────────────────────────────────────────────────────┤
│ ✅ 黄金高度 (The Right Altitude / 目标明确 + 边界清晰)      │
│ "背景是什么 + 达成什么具体目标 + 遵循什么约束 + 如何自测验收"│
│ 后果: 目标绝对明确，留给模型足够的战术空间，且结果可验证    │
└─────────────────────────────────────────────────────────────┘
```

### 1. 结构化指令黄金四要素（BGCO 模板）
每一次给 Agent 派发具体的编程任务时，采用结构化的四段式指令：

```text
## 1. Background (背景上下文)
我们的后端服务基于 Node.js/Express 开发，当前正在完善用户认证模块。

## 2. Goal (核心交付目标)
在 src/controllers/auth.ts 中实现用户注销（Logout）接口，使当前 Token 失效。

## 3. Constraints (不可逾越的边界红线)
- 仅修改 auth.ts 与对应的路由文件，严禁碰触数据库连接池配置；
- 必须遵循 RESTful 规范，接口路径定为 POST /api/v1/auth/logout；
- 错误处理统一抛出现有的 AppError，禁止使用原生的 throw new Error()。

## 4. Output & Verification (验证标准)
修改完成后，必须在终端执行 `pnpm test tests/auth.test.ts`，确保测试用例全部通过。
```

### 2. 用少样本示例（Few-Shot）替代万字长文
大语言模型是天然的“模式匹配大师”。  
用一万字去给它解释“什么是正向因果叙述”，远不如直接甩给它两组对照例子：

```markdown
请严格遵循以下代码改写规范：
- ❌ 错误示范：这不是电脑配置差，而是你装了流氓软件。
- ✅ 正确示范：电脑变慢的物理原因，是后台被静默启动了多个高占用常驻进程。
```
看到真实例子的瞬间，模型会自动在神经网络底层完成模式对齐，准确率立竿见影。

## 二、Skills 机制：渐进式披露的领域特种兵包

学会了写好单次 Prompt，我们很快会面临下一个工程痛点：  
项目里往往有很多非常深奥、非常专业的领域特定知识。例如：
- 如何遵循大厂标准的 Conventional Commits 规范进行原子化 Git 提交；
- 如何按照 OWASP Top 10 安全标准扫描后端代码中的 SQL 注入与 XSS 漏洞；
- 如何调用 Playwright 自动化驱动无头浏览器执行前端视觉回归测试。

**如果把所有这些几十页的特种专业文档，全部一股脑塞在每一次对话中，会产生严重的工程灾难**：
1. **撑爆上下文窗口（Context Bloat）**：每次对话都要重复消耗几万 Token，不仅贵，而且速度变慢；
2. **注意力稀释（Attention Decay）**：根据大模型注意力机制的物理特性，提示词塞得越满，模型抓重点的能力就越差，反而容易把核心业务指令漏掉。

为了解决这一矛盾，现代顶级 Agent（如 OpenCode、Claude Code、Hermes）普遍采用了 **Skills（技能包）机制**。它的核心设计哲学是——**渐进式披露（Progressive Disclosure）**。

```text
┌─────────────────────────────────────────────────────────────┐
│ 常驻 Agent 视野 (仅消耗 ~200 Tokens 路由元数据)             │
│ - Skill 1: [git-master] 专业 Git 原子提交与变基专家         │
│ - Skill 2: [api-security-audit] OWASP 接口安全漏洞扫描专家  │
│ - Skill 3: [browser-testing] Playwright 自动化浏览器视觉测试 │
└──────────────────────────────┬──────────────────────────────┘
                               │
               用户提问: "帮我审查一下后端登录接口的安全性"
                               │
                               ▼ Agent 意图识别命中！
┌─────────────────────────────────────────────────────────────┐
│ 触发动态按需加载 (JIT / Progressive Disclosure)             │
│ Agent 瞬间从磁盘读取并挂载完整的 security-audit/SKILL.md    │
│ 临时获得全套高危注入检测规则、鉴权防护规范与修复模式指南！   │
└─────────────────────────────────────────────────────────────┘
```

### 1. Skills 的标准物理结构
一个典型的 Skill 通常以文件夹的形式保存在通用技能目录下（如全局的 `~/.config/opencode/skills/`、项目的 `.opencode/skills/`，或者 Claude 的 `.claude/skills/`）：

```text
skills/
└── api-security-audit/
    ├── SKILL.md        ← 技能的核心大脑说明书 (规范与模式)
    └── scripts/        ← 配套自动化扫描或验证脚本 (可选)
```

### 2. `SKILL.md` 的精妙设计
打开 `SKILL.md`，你会看到它由两部分组成：

```markdown
---
name: api-security-audit
description: Web 后端接口安全审计专家。专门用于检测 SQL 注入、未授权水平越权、密码未哈希存储、敏感凭证泄露等高危安全漏洞。
---

# API 安全审计专家规范

当用户要求审计代码安全性、检查 API 漏洞或发布前安全复核时，触发本技能：
1. 检查所有涉及数据库的查询，强制验证是否使用了参数化查询 (Prepared Statements)，严禁字符串直接拼接 SQL；
2. 检查密码与 Token 处理，确认是否使用了 Argon2id 或 bcrypt 加密，严禁明文比对；
3. 检查返回给前端的 JSON 数据中是否无意泄露了手机号、身份证或内部密钥字段。
```

- **头部 YAML 元数据（`description`）**：这是**路由信号灯**。Agent 在平时只读这一句简短的描述（仅占几十个 Token），用来判定当前任务是否跟它相关；
- **下方正文**：只有当用户的任务明确命中了这项技能时，Agent 才会把它完整吞入上下文显存中。**任务结束，技能随之卸载，保证主干上下文永远轻盈纯净！**

## 三、`AGENTS.md`：长效驻留的项目宪法

如果说 Prompt 是一次性的口头指令，Skills 是按需调用的参考书，那么 **`AGENTS.md`（或 `CLAUDE.md`）就是整个代码仓库的“基本法”**。

它存放在项目的根目录下，每一个启动的 Agent、每一个派生出的子智能体，在动手触碰任何文件之前，**第一个动作必然是静默读取这份文件**。

```text
[ 唤起任何终端 Coding Agent ]
            │
            ▼ 强制前置动作
读取当前仓库根目录下的 【AGENTS.md】
            │
            ▼ 瞬间确立项目认知底线
┌────────────────────────────────────────────────────────┐
│ - 锁定技术栈: 必须用 pnpm，绝对禁止 npm/yarn           │
│ - 划清目录边界: 源码只在 src/，产物在 dist/，禁止乱窜   │
│ - 严守代码红线: 必须使用 TypeScript，严禁直接加 any    │
│ - 明确自测规则: 交付前必须在终端自跑测试套件           │
└────────────────────────────────────────────────────────┘
```

### 1. 通用全栈项目 `AGENTS.md` 黄金实战模板
你可以直接把以下模板复制并根据你的具体项目微调，放置在工程的根目录下：

```markdown
# 项目工程规范与 Agent 协作宪法

## 1. 技术栈与环境底座
- **项目类型**：前后端分离的全栈 Web 工程
- **包管理器**：必须且仅能使用 `pnpm`（版本 >= 9.x），**严禁使用 npm 或 yarn**，避免破坏 lockfile
- **代码语言**：TypeScript (严格模式开启)，**严禁在未说明原因的情况下使用 `as any`**
- **代码风格**：函数采用小驼峰（`camelCase`），类名采用大驼峰（`PascalCase`），文件名采用短横线（`kebab-case`）

## 2. 核心目录架构与职责划分
- `src/client/`：前端界面源码 (React / Vue 组件与样式)
- `src/server/`：后端服务源码 (Controller 控制层、Service 业务层、Model 数据层)
- `src/types/`：前后端共用的 TypeScript 类型与数据契约定义
- `tests/`：自动化测试目录 (单元测试与集成测试)
- `dist/`：构建编译产物目录 (严禁手动修改)

## 3. 严格代码与架构红线（违反即视为交付失败）
- **RESTful 规范**：所有 API 接口路径必须严格采用名词复数，操作全部使用 HTTP 动词映射；
- **环境隔离**：任何数据库密码、第三方 API Key 严禁硬编码在代码中，必须读取 `.env` 环境变量；
- **不可逆保护**：严禁执行任何会清空数据库或物理删除大量文件的破坏性脚本；
- **提交规范**：所有 Git 提交必须遵循 Conventional Commits 规范 (如 `feat:`, `fix:`, `docs:`)。

## 4. 交付验收流水线（修改完毕后必须在终端闭环验证）
- 静态类型检查：`pnpm tsc --noEmit`（零类型报错）
- 自动化测试回归：`pnpm test`（确保所有单测与集成测试 100% 通过）
```

### 2. 为什么写好 `AGENTS.md` 几乎不花钱？
还记得我们在上一篇学到的 **Prompt 缓存机制（Prompt Caching）** 吗？
- `AGENTS.md` 存放在项目根目录，它的内容通常是高度稳定的，不会每分钟都改变；
- 当 Agent 多次调用大模型时，这段固定在最前面的项目宪法，会稳定触发服务端的 **Cache Hit（缓存命中）**，享受高达 90% 以上的费用减免与毫秒级的加载速度！
- **花极少的 Token 代价，换取 Agent 全程不跑偏、不违规，这是全网最具性价比的工程投资。**

## 四、指令、技能与宪法的协同全景图

至此，一个专业开发者与 Coding Agent 沟通的**三层立体防御网络**已经彻底合围：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 【第三层：AGENTS.md (项目宪法 - 范围最广，长效驻留)】                  │
│ 规定项目的全局技术栈、目录禁区、代码红线与强制验收命令                 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 【第二层：Skills 技能包 (特种专家 - 按需插拔，渐进式披露)】            │
│ 当遇到特定复杂领域（如写样式、测安全、跑浏览器）时才动态挂载           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 【第一层：单次 Prompt (微观指令 - 目标明确，BGCO 结构)】                │
│ 本次具体要解决的问题、精准输入输出与特定交付边界                       │
└────────────────────────────────────────────────────────────────────────┘
```

有了这三层坚不可摧的工程体系做护栏，无论你使用的是 Claude Code、OpenCode、Codex 还是 pi，Agent 都能从一个脱缰野马般的“概率复读机”，瞬间蜕变成为一个**严谨、守规矩、高质量交付的专业级虚拟工程师**。
