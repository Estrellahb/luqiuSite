# 现代 AI 编程工程体系：从提示词、上下文、Spec 驱动到 Harness 底座

当大多数人对 AI 编程的认知还停留在"怎么写出更巧妙的提示词（Prompt Engineering）"时，全球顶尖的人工智能实验室与软件工程工业界，早已将战场推进到了更加宏大、深邃的**工程系统级维度**。

如果你曾经让 Coding Agent 连续工作数小时、处理跨越几十个文件的复杂任务，你必然遭遇过这些诡异的现象：
- *"明明刚开始很聪明，聊到第 20 轮对话时，它突然开始‘装傻’，连第一轮说好的规则都忘得一干二净；"*
- *"现在的模型明明号称支持 100 万甚至 200 万 Token，但当你把整个代码仓库一股脑全塞给它时，它给出的代码反而质量暴跌、幻觉频发；"*
- *"Agent 陷入了死循环：改了报错、报了再改、改回原样、无限打转……"*

这些故障的根源在于：**在长周期、大规模的真实软件开发中，光靠“优化提示词”已经触碰到了物理天花板。**

近两年来，学术界（如顶刊论文 *Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents*）与行业先驱（如 Martin Fowler）共同确立了一套全新的认知分层。

本篇我们将带你登上现代 AI 编程的技术珠穆朗玛峰，彻底拆解 **AI 编程工程体系的四大演进阶梯（Prompt → Context → Spec → Harness）**。

---

## 一、AI 软件工程进化的四大梯队（The Lineage）

软件工程在面对 AI 时，经历了四次工作重心的逐级跃迁：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 第四级：Harness Engineering (支架工程 - 终极底座)                      │
│ 关注【运行环境】：构建安全护栏 Hooks、工具分发、执行循环与自愈基建     │
│ 核心公式：Agent = Model + Harness                                      │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 包含与支撑
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 第三级：Spec-Driven Development (规格驱动开发 - 需求蓝图)              │
│ 关注【确定性契约】：用可执行的 Spec (验收标准/数据契约) 替代模糊口头诉求│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 包含与支撑
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 第二级：Context Engineering (上下文工程 - 视野管理)                    │
│ 关注【信息架构】：管理整个上下文窗口，对抗注意力衰减、动态压缩与隔离   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 包含与支撑
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 第一级：Prompt Engineering (提示词工程 - 微观表达)                     │
│ 关注【单次指令】：优化单次调用的语气、结构化模板与少样本对齐           │
└────────────────────────────────────────────────────────────────────────┘
```

- **Prompt Engineering（提示词工程）**：优化**单次调用的那一句话**；
- **Context Engineering（上下文工程）**：优化**模型在推理时眼之所及的整个信息世界**；
- **Spec-Driven Development（规格驱动开发）**：在动手前确立**不可推翻的机器可读契约**；
- **Harness Engineering（支架工程）**：把大模型像发动机一样安装进一台**具备制动器、转向盘与防撞梁的坚固赛车底盘**中。

## 二、Context Engineering（上下文工程）：把有限注意力当做稀缺资源

很多新手会有一个直觉误区：“既然现在的模型上下文窗口都有 100 万 Token 了，那我就把项目所有文件、全网文档、几十万字全塞进去，它不就全知全能了吗？”

**答案是：绝对不行。这在学术界被称为“上下文腐化（Context Rot）与注意力稀释”。**

根据注意力机制（Attention Mechanism）的物理定律，当输入的信息量呈指数级增长时，有效信息之间的信噪比（SNR）会断崖式暴跌，模型的深层推理精度急剧下滑。**上下文工程的核心思想，就是将上下文窗口视为极其珍贵、极其昂贵的“战术显存”，极力推行“最小必要信息（Minimal Sufficiency）”原则。**

```text
全量粗暴塞入 (Bad):
[ 50个无关文件 + 上百条工具报错日志 + 几万行历史对话 ] ──→ 大模型注意力瘫痪，开始胡言乱语

上下文工程精细治理 (Good):
[ 核心项目宪法 (AGENTS.md) ] 
       + [ 正在处理的目标文件 (JIT 懒加载) ] 
       + [ 经过压缩提炼的决策摘要 (Compaction) ] ──→ 视野纯净，逻辑严密，极速高保真交付
```

现代成熟 Agent（如 OpenCode、Claude Code、Codex）在底层普遍部署了三大上下文治理重器：

### 1. 动态上下文压缩（Adaptive Context Compaction）
在长时会话中，Agent 执行的每一步终端命令都会向上下文倾倒大量的字符日志（例如跑一次构建吐出几百行）。
- 当对话接近 Token 预算警戒线时，Agent 会自动触发**渐进式压缩算法（Compaction）**；
- **清洗废弃物**：物理剔除掉过去几轮中已经失效的冗长终端输出日志，仅仅保留一句话结论：“已在第 3 轮成功执行构建验证”；
- 这种机制能瞬间为显存腾出 70% 以上的空间，让会话能够长青运行数天而不崩溃。

### 2. 事件驱动系统提醒（System Reminders）
大模型在对话进行到深水区时，容易对最初设立的系统 Prompt 产生“注意力钝化（Attention Fade-out）”。  
上下文工程会在关键的事件节点（例如：当 Agent 即将调用写文件工具前），通过底层 Hook 自动向上下文尾部注入一句极轻量但权重极高的**实时便签提醒**：
> *`[System Reminder: 请再次确认，修改后的代码是否严格遵循了规范命名，并请准备好自测命令]`*  
这就像在跑道弯道处立下的反光警示牌，瞬间唤醒大模型的自律意识。

### 3. 子智能体隔离（Subagents as Context Isolation）
当需要在一堆陌生文件中搜寻某一个配置时：
- 传统做法：主 Agent 自己翻看 20 个文件，这 20 个文件的全部内容都会硬生生挤进主对话上下文中，造成不可逆的污染；
- 上下文工程做法：主 Agent 派生出一个临时的**探索子智能体（Explore Worker）**；
- 子智能体在一个**完全独立的临时空白窗口**中尽情翻看 20 个文件，提炼出最终结论后，只向主控 Agent 发回一段 200 字的精准摘要，随后子进程直接销毁！**主控窗口仅消耗 200 Token，就获得了原本需要消耗 2 万 Token 才能得到的关键情报。**

## 三、Spec-Driven Development（规格驱动开发）：从猜测到确定性工程

在软件工程演进中，**“在没有蓝图的情况下让工人直接砌砖，房子必然倒塌”**。

在 AI 时代，如果你只给 Agent 一句话：“帮我做个用户管理后台”，Agent 就会基于它看过的全网代码库自由发挥——今天用这套加密算法，明天设计那套表结构，后天随手引入三个新依赖。**这被称为“非确定性黑盒灾难”。**

为了彻底根除这种不确定性，当前工业界最推崇的开发范式是 **Spec-Driven Development（规格驱动开发，简称 SDD）**。

```text
传统随意模式 (Prompt-Driven):
用户随口一句话 ──→ AI 瞎猜实现 ──→ 疯狂返工修 Bug ──→ 最终代码失控

规格驱动模式 (Spec-Driven):
用户提出宏观目标 ──→ 【第一阶段: 编制可执行 Spec 蓝图】 (确定数据契约/边界/测试用例)
                          │ 人机共同审核封版
                          ▼
                   【第二阶段: 机械式落地实现】 (AI 严格按照 Spec 施工，零自由发挥)
                          │
                          ▼
                   【第三阶段: 自动化对标验收】 (所有测试与 Spec 100% 对齐)
```

### 1. 什么是真实的“Spec（工程规格书）”？
一份工业级的 Spec 是一份**具备机器可读性、由具体数据契约构成的结构化技术文档**，它通常包含三大要素：
1. **Requirements（精确需求）**：用严格的用户故事描述，绝不含糊；
2. **Data Contracts（数据契约与接口设计）**：白纸黑字锁死每个 API 接收什么参数、返回什么 JSON，状态码怎么抛；
3. **Acceptance Criteria（验收测试准则）**：列出清晰的红绿清单（Checklist）与具体的断言条件（例如：“当传入非法邮箱时，接口必须返回 400 且附带错误字段”）。

### 2. 为什么 Spec 是多 Agent 并发协同的前提？
如果我们要同时唤醒 5 个 Agent 在不同的子模块中并行写代码：
- 没有 Spec，5 个 Agent 会各自发明一套接口和数据类型，最后拼装时必然产生剧烈的代码冲突；
- 有了 Spec，它就是全军必须遵守的“共同作战法典”。每个 Agent 各自领走一个子任务，严格按照契约施工，最终无缝合并。

## 四、Harness Engineering（支架工程）：Agent = Model + Harness

2026 年，软件架构大师 **Martin Fowler** 与顶刊论文共同确立了关于 AI Agent 的核心定义公理：

==**Agent = Model + Harness**==

> **“大模型（Model）只是引擎，而真正决定一台赛车能否以 300 公里时速稳定行驶在赛道上的，是外围的底盘、悬挂、转向机、行车电脑与刹车系统——这就是支架工程（Harness Engineering）。”**

许多自制或低劣的 Agent 之所以动不动就改崩系统、陷入死循环，根本原因在于**包裹在大模型外围的 Harness 过于简陋脆弱**。

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                      【Agent Harness 支架工程全景】                     │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ 1. 前馈引导层 (Guides / Feed-forward)                             │  │
│  │    在行动前进行航向约束 (AGENTS.md、Spec 契约、类型系统)           │  │
│  └─────────────────────────────────┬─────────────────────────────────┘  │
│                                    │                                    │
│                                    ▼                                    │
│                      ┌───────────────────────────┐                      │
│                      │    核心大脑 (The Model)   │                      │
│                      │   推理推演、生成拟操作    │                      │
│                      └─────────────┬─────────────┘                      │
│                                    │ 准备调用系统工具                   │
│                                    ▼                                    │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ 2. 硬性安全护栏 (Hooks & Guardrails / 拦截层)                     │  │
│  │    在底层操作系统层面硬拦截高危动作 (退出码为 2，拦截率 100%)     │  │
│  │    - 严禁对保护分支进行 force push                                │  │
│  │    - 严禁执行未经确认的 rm -rf 破坏性指令                         │  │
│  │    - 探测死循环并强制刹车熔断 (Doom Loop Breaker)                 │  │
│  └─────────────────────────────────┬─────────────────────────────────┘  │
│                                    │ 放行安全动作，执行操作             │
│                                    ▼                                    │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ 3. 反馈感应层 (Sensors & Feedback)                                │  │
│  │    在行动后提供客观事实审判                                       │  │
│  │    - 自动跑编译器 (tsc)、静态分析 (Linter) 与测试套件             │  │
│  │    - 调度独立的质量审查子智能体 (Reviewer) 进行语义复核           │  │
│  └───────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1. 软约束 vs 硬拦截：为什么必须有 Hooks？
很多开发者试图通过在提示词里苦苦哀求 AI：“请你千万不要删除数据库、千万不要推主分支”。  
**但在概率系统面前，任何纯靠 Prompt 的约束，合规率通常只有约 70% 到 80%。在生产环境中，这意味着早晚会出现致命事故。**

Harness Engineering 的核心原则是：**用系统底层代码（Hooks）实行 100% 确定性的物理硬拦截**：
- 在调用任何 Bash 指令前，Harness 的安全钩子会先在操作系统底层扫描命令模式；
- 一旦匹配到高危越权指令，底层直接抛出硬性阻断信号（Exit Code 2），**大模型根本没有物理权限执行该操作，彻底消灭安全隐患**。

### 2. 死循环熔断器（Doom Loop Detection）
当代码出现顽固报错时，缺乏 Harness 保护的 AI 会在同一个错误里来回尝试几十遍，白白烧光数百万 Token。  
一个优秀的 Harness 会内置状态哈希检测：
- 一旦发现 Agent 连续 3 次产生了相同的文件修改、或者在同一个错误日志上停滞不前；
- Harness 会主动介入中断当前的死循环，强行重置思路，甚至自动唤醒一个更具深度推理能力的审查专家从全新角度切入。

## 五、全篇总结：站在现代软件工程的最前沿

从最初的提示词，到今天的全套工程体系，我们梳理出了一张现代 AI 编程的终极对照图谱：

| 工程维度 | 核心关注点 | 解决什么问题？ | 典型代表工具/产物 |
| :--- | :--- | :--- | :--- |
| **Prompt Engineering** | 单次指令的精准表达 | 消除日常意图的含糊不清 | BGCO 模板、少样本 Few-Shot |
| **Context Engineering** | 模型信息视野的精细治理 | 终结 Token 浪费与注意力衰减 | 动态压缩、Skills 按需披露、子 Agent 隔离 |
| **Spec-Driven** | 机器可读的确定性蓝图 | 彻底消灭 AI 凭空臆造与自由发挥 | API 契约、架构规格书、前置测试用例 |
| **Harness Engineering** | 环绕大模型的安全生产底座 | 构筑 100% 硬防线与全自动自愈闭环 | OpenCode/Codex 运行时、Hooks 拦截器、死循环熔断 |
